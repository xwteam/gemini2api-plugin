## 💡 工作原理

中轉站部署在資料中心 IP 上，Google 對這類 IP 的登入工作階段約 2 小時強制失效。但**你本地瀏覽器跑在住宅 IP 上，同一帳號的工作階段能存活更久**。本擴充功能正是利用這一點，分兩條線工作：

```
① 主動同步（v1.3.0）：瀏覽器自己輪換了 Cookie → 及時轉交中轉站
chrome.cookies.onChanged 發現 __Secure-1PSIDTS / __Secure-1PSID 變化
  → 等約 10 秒合併連續變化 → 讀取目前 Cookie（不重新整理分頁）
  → 目標帳號：側邊欄綁定的帳號 ID；沒綁定就依 PSID 比對
  → 與上次成功推送的不同、且距上次推送 ≥ 60 秒 → PUT /admin/accounts/{id}/cookies
  （每次定時輪詢也補查一次，防止 service worker 被回收而漏推）

② 救火：每隔 N 秒 → GET /admin/status 查中轉站帳號狀態
  ├─ 其餘狀態 → 什麼都不做
  └─ expired（過期），或 v1.6.41～v1.6.43 的中轉站仍回報 active 但 is_healthy=false（工作階段失效）
        → 都在冷卻期、或（未綁定帳號 ID 時）本地 PSID 都對不上 → 不重新整理，等下一輪
        → 重新整理本地已開啟的 gemini.google.com 分頁
        → chrome.cookies 讀取新的 __Secure-1PSID / __Secure-1PSIDTS
        → PUT /admin/accounts/{id}/cookies 提交給中轉站
        → 下一輪輪詢驗證是否恢復 active
```

擴充功能自己從不輪換 Cookie：主動同步只是把瀏覽器已經換好的值轉交給中轉站；平時不操作瀏覽器，**只有檢測到過期 / 工作階段失效、且確有帳號要提交時才重新整理一次分頁**，並設冷卻期防止重複重新整理。兩條線提交時都帶請求標頭 `X-Gemini2API-Keepalive: gemini2api-plugin/<版本>`：**gemini2api ≥ v1.6.44** 據此把該帳號標為「瀏覽器保活」、不再由伺服器端輪換，避免瀏覽器與中轉站互相頂掉對方的 PSIDTS；舊版中轉站會忽略這個標頭。

## 🌟 核心特性

- **主動同步（v1.3.0）**：瀏覽器輪換 Cookie 後約 10 秒內推給中轉站；只在值變化時推，同一帳號至少間隔 60 秒，定時輪詢兜底補推；擴充功能本身不輪換 Cookie、不重新整理頁面
- **救火**：帳號過期，或 v1.6.41～v1.6.43 的中轉站仍回報 active 但 `is_healthy=false`（工作階段失效）時，重新整理分頁並提交新 Cookie；冷卻期內、或未綁定帳號 ID 且本地 PSID 對不上時不重新整理；其餘時間不操作瀏覽器
- **讀取 HttpOnly Cookie**：借助擴充功能的 `chrome.cookies` 權限讀取網頁 JS 讀不到的 `__Secure-` 認證 Cookie
- **靜默重新整理**：自動重新整理已開啟的 Gemini 分頁，無需手動操作
- **按帳號提交 + 防串號**：填了帳號 ID 就按帳號直接提交新 Cookie（這是保活關鍵——Cookie 變了也能提交覆蓋）；沒填帳號 ID 時靠本地 PSID 自動匹配帳號，避免多帳號串號
- **冷卻防抖**：同一帳號重新整理後進入冷卻期，避免連續多輪重複打架
- **側邊欄常駐**：以瀏覽器右側固定側邊欄展示，操作時不消失，方便長時間盯著保活狀態和動作日誌
- **多語言介面**：擴充功能 UI 與日誌自動跟隨 Chrome 瀏覽器語言（簡中 / 繁中 / 英 / 日 / 韓），與文檔語言一致
- **零依賴**：純原生 JavaScript + Manifest V3，無需建置、無第三方函式庫
- **隱私安全**：API Key 與 Cookie 只存本地、只發往你配置的中轉站；同步記錄只存 Cookie 的雜湊指紋，不另存原值

## 📦 安裝

> [!TIP]
> 適用於 Chrome、Edge 等 Chromium 核心瀏覽器。

1. 下載/複製本倉庫到本地
2. 開啟擴充功能管理頁：Chrome 為 `chrome://extensions`，Edge 為 `edge://extensions`
3. 開啟右上角的 **開發人員模式**
4. 點擊 **載入未封裝項目**，選擇本專案根目錄（含 `manifest.json` 的資料夾）

> [!IMPORTANT]
> 請載入含 `manifest.json` 的本倉庫根目錄。本倉庫**僅含擴充功能執行檔、靜態文檔**（`docs/`）**與單元測試**（`tests/`，擴充功能執行時不會載入；開發者可用 Node ≥ 22 執行 `node --test tests/`），不含文檔生成腳本等非擴充檔案。

5. 安裝後點擊擴充功能圖示 → 在右側開啟側邊欄：
   - 頂部 **綁定本瀏覽器負責的帳號 ID**（如 `account-0`）
   - 右上角 **中轉站設定** 填寫地址和 API Key（見下文）

## ⚙ 配置說明

### 側邊欄（本瀏覽器實例）

| 配置項 | 說明 |
|--------|------|
| **帳號 ID** | **強烈建議填寫**（如 `account-0`）。一個瀏覽器實例只保活一個帳號，在此綁定；多帳號時每個瀏覽器設定檔各填各的 |

填寫後點 **綁定**。留空則靠 PSID 自動匹配（精度較低，不推薦多帳號場景）。

### 中轉站設定頁

| 配置項 | 說明 |
|--------|------|
| **中轉站地址** | 你的 Gemini2API 地址，如 `http://1.2.3.4:5918` |
| **API Key** | 中轉站的 `sk-` 開頭金鑰；若 gemini2api ≥ v1.6.16 配置了獨立 `ADMIN_API_KEY`，此處應填**管理金鑰** |
| **輪詢間隔** | 多久查一次狀態，預設 60 秒，最小 30 秒 |
| **重新整理冷卻** | 救火時同一帳號重新整理後多久內不重複處理，預設 120 秒（主動同步另有固定的 60 秒最小間隔） |

填好後點 **測試連線** 確認能連上中轉站，再點 **儲存**（儲存時瀏覽器會請求存取該中轉站網域的權限，請點允許）。

> [!NOTE]
> **gemini2api 版本相容**：
> - v1.6.16 起 `/admin/status` 對 PSID 脫敏返回。未填帳號 ID 時擴充功能用 PSID 首尾片段自動匹配。**強烈建議始終填寫帳號 ID**，最可靠且避免串號。
> - v1.6.40 及更早版本提交 Cookie 後不會更新 `/admin/status` 裡該帳號的 PSID 記錄。若中轉站帳號當初填的是別的工作階段（如無痕視窗）的 Cookie，綁定模式下主動同步會因 PSID 對不上而跳過（日誌有提示），只剩過期救火；升級中轉站後按一次「強制重新整理提交」即可。
> - v1.6.41～v1.6.43 對 Google 工作階段已失效的帳號仍回報 `active`，只把 `is_healthy` 設為 false；擴充功能（v1.3.0 起）按「工作階段失效」去救。
> - **v1.6.44 起**，被 Google 打回登入頁的帳號直接回報 `expired`；仍回報 `active` 但 `is_healthy` 為 false 只表示中轉站自身暫時不健康（網路抖動、5xx、剛啟動等），換 Cookie 也沒用，擴充功能顯示「不健康」、不重新整理也不提交（擴充功能看 `/admin/status` 有沒有 `keepalive_mode` 欄位來區分新舊版本）。
> - **v1.6.44 起**，擴充功能推送過 Cookie 的帳號會被標為「瀏覽器保活」（`/admin/status` 裡 `keepalive_mode` 為 `browser`），伺服器端不再輪換它。想讓某個帳號改回伺服器端輪換（例如改用無痕視窗取的 Cookie），先在對應瀏覽器裡停用本擴充功能，再到面板手動更新 Cookie——否則擴充功能下次同步又會把它標回瀏覽器保活。

> [!IMPORTANT]
> **一個瀏覽器實例只能保活一個帳號。** 瀏覽器對 `gemini.google.com` 只有一份 Cookie，擴充功能讀到的永遠是當前登入的那個帳號。所以：
> - 瀏覽器裡要**常開一個已登入的 `gemini.google.com` 分頁**，且登入的就是你要保活的那個帳號。
> - **強烈建議用獨立的瀏覽器環境專門跑保活**（獨立使用者設定檔 / 無痕視窗 / 指紋瀏覽器），不要和你日常登入其它 Google 帳號的瀏覽器混用，否則重新整理時會讀到錯誤帳號、造成串號或互相干擾。
> - 在側邊欄頂部**綁定本瀏覽器負責的帳號 ID**（多帳號時每個設定檔各綁一個，不要共用）
> - 分頁或瀏覽器關閉後，該帳號過期將無法自動修復。

## 👥 多帳號使用

中轉站有多個帳號時，**每個帳號用一個獨立瀏覽器環境分別登入、各裝一個本擴充功能**：

| 帳號 | 瀏覽器環境 | 登入的 Google 帳號 |
|------|-----------|-------------------|
| account-0 | Chrome 設定檔 A / 指紋瀏覽器視窗 1 | 帳號 0 的 Google |
| account-1 | Chrome 設定檔 B / 指紋瀏覽器視窗 2 | 帳號 1 的 Google |
| …… | …… | …… |

每個環境裡的擴充功能：**中轉站設定**填同一個地址和 API Key；**側邊欄頂部**各綁不同的帳號 ID（如 A 綁 `account-0`、B 綁 `account-1`）。這樣多個瀏覽器各管各的帳號，互不干擾。

> [!TIP]
> 推薦用 Chrome 的「使用者 / 設定檔」功能或指紋瀏覽器，為每個帳號開一個完全隔離的環境，Cookie 互不影響。無痕視窗也可，但關閉即失效、需重新登入。

## 🖥 介面說明

點擊工具列圖示會在瀏覽器**右側開啟固定側邊欄**（常駐不消失，方便長時間盯著保活狀態和日誌）。

- **側邊欄面板**：頂部綁定本瀏覽器負責的**帳號 ID**；下方顯示帳號活動 / 過期 / 工作階段失效 / 不健康狀態、PSID 打碼預覽、最近動作日誌（含主動同步記錄）；`立即檢查` / `強制重新整理提交`；右上角 **中轉站設定** 進入連線配置頁。
- **本地 Cookie 區**：顯示本地瀏覽器當前讀到的 `__Secure-1PSID` / `__Secure-1PSIDTS`（預設打碼，可點 `👁 顯示完整` 看全值），並提示是否與中轉站帳號匹配——方便排查「到底有沒有讀到 Cookie、是不是對的帳號」。
- **圖示角標**：
  - 藍色數字 = 活動帳號數
  - 紅色數字 = 過期或工作階段失效（待救）的帳號數
  - `!` = 連線中轉站失敗

## 🔐 權限說明

| 權限 | 用途 |
|------|------|
| `cookies` + `*://*.google.com/*` | 讀取 Gemini 的 HttpOnly 認證 Cookie，並監聽其變化以主動同步 |
| `tabs` | 查找並重新整理 gemini.google.com 分頁 |
| `storage` | 儲存配置、動作日誌與同步記錄（只存雜湊指紋） |
| `alarms` | 定時輪詢 |
| 中轉站網域權限 | 儲存設定時按你填寫的地址動態申請 |

> [!NOTE]
> **隱私承諾**：API Key 和讀取到的 Cookie 僅儲存在本地瀏覽器，且只發送給你配置的中轉站地址，絕不發往任何第三方。v1.3.0 的主動同步沒有新增任何權限，同步記錄只保存 Cookie 的 SHA-256 截斷指紋，不另存 Cookie 原值。

## ❓ 常見問題

**Q：擴充功能提示「未找到 gemini.google.com 分頁」？**
A：請在瀏覽器裡開啟並登入 https://gemini.google.com ，保持該分頁常開。

**Q：重新整理後仍讀不到 Cookie？**
A：說明本地瀏覽器當前也未登入 Gemini，或登入的不是中轉站使用的帳號。請重新登入。

**Q：狀態一直顯示過期、提交後不恢復？**
A：可能是 Google 已吊銷該帳號的主工作階段（PSID 被吊銷無法靠重新整理恢復）。此時需要重新登入 Gemini 獲取全新 Cookie。

**Q：帳號沒過期，擴充功能為什麼也在提交 Cookie？**
A：這是 v1.3.0 的主動同步。瀏覽器與中轉站共用同一個 Google 工作階段，瀏覽器輪換出新的 PSIDTS 後，中轉站手裡的舊值很快會失效，所以擴充功能把新值及時轉交過去（只在值變化時推，同一帳號至少間隔 60 秒，不重新整理分頁）。搭配 gemini2api ≥ v1.6.44，中轉站會停止自行輪換這個帳號，避免兩邊互相頂掉。

**Q：側邊欄顯示「工作階段失效」或「不健康」是什麼意思？**
A：兩者都是中轉站仍回報 `active` 但 `is_healthy` 為 false，差別在中轉站版本。「工作階段失效」只出現在 gemini2api v1.6.41～v1.6.43：這幾版對 Google 工作階段已失效的帳號就是這樣回報的，擴充功能把它和「已過期」一樣處理——重新整理分頁並提交新 Cookie（這幾版裡網路抖動等原因造成的不健康也會被當成工作階段失效）。v1.6.44 起被打回登入頁的帳號直接回報 `expired`，仍回報 `active` 但不健康只說明中轉站自身有問題（網路抖動、5xx、剛啟動等），並非登入失效：擴充功能顯示「不健康」，不重新整理分頁也不提交，請到中轉站面板 / 日誌排查。

**Q：會不會讓帳號被封？**
A：擴充功能不會額外請求 Google：主動同步只把瀏覽器已有的 Cookie 轉交給中轉站，只有救火時才重新整理一次分頁，操作頻率極低；但任何非官方方式都有風險，請自行評估。

**Q：多帳號會不會把 A 帳號的 Cookie 提交給 B 帳號（串號）？**
A：沒綁定帳號 ID 時，擴充功能只提交給本地 PSID 對得上的帳號，對不上（或同時對上多個）就不提交。綁定了帳號 ID 時以綁定為準：帳號狀態正常時，主動同步發現本地 PSID 與該帳號在中轉站的記錄不一致（例如本瀏覽器改登了別的 Google 帳號）會跳過並在日誌裡提示，不覆蓋中轉站上正常的工作階段；但帳號過期 / 工作階段失效需要救火、或你手動按「強制重新整理提交」時，仍會照綁定提交（不校驗 PSID，日誌會註明不一致）。所以前提仍是**一個瀏覽器只登入一個帳號**，多帳號請用獨立瀏覽器環境分別跑（見「多帳號使用」）。

**Q：提示 `Cannot load extension with file or directory name _doc_templates`？**
A：請更新到 **v1.2.2+** 並重新拉取倉庫。v1.2.3 起已移除所有文檔生成工具，倉庫內僅保留擴充功能與靜態 `docs/`。

## ⚠ 已知限制

- **一個瀏覽器只能保活一個帳號**：瀏覽器對 Gemini 只有一份 Cookie。多帳號必須用多個獨立瀏覽器環境（設定檔 / 無痕 / 指紋瀏覽器）分別登入、各裝一個擴充功能。
- **不保證突破 2 小時**：本地瀏覽器與中轉站共用同一 Google 工作階段。gemini2api v1.6.41～v1.6.43 的伺服器端也會定時輪換 PSIDTS，兩邊可能互相頂掉；升級到 v1.6.44 及以上，擴充功能推送過的帳號才會停掉伺服器端輪換。實際效果需觀察。
- **依賴瀏覽器常駐**：瀏覽器或 Gemini 分頁關閉後即停止保活（主動同步也靠開著的 Gemini 分頁讓瀏覽器持續輪換 Cookie），這是「不主動頻繁重新整理」設計的固有取捨。
